01

Whole-project overview

Read by number: which file does what?

A2 creates the prediction model; A3 uses it to check user-submitted URLs. These steps match the overview diagram. Parts 02 and 03 expand the intermediate steps.

  1. 1

    malicious_phish.csv contains the original URLs and known labels. This is the starting data for A2, not a trained model.

  2. 2

    feature_extraction.py receives cleaned data and converts URL characteristics into numbers. These numbers become the inputs the model learns from.

  3. 3

    train_classifier.py learns from train and compares models using validation. The selected model still needs final evaluation and packaging.

  4. 4

    final_pipeline.joblib stores the trained model together with its fitted preprocessing. A3 reads this file to predict without learning again from scratch.

  5. 5

    CheckUrlPage.jsx is where users enter a new URL and wait for results. This page does not run the Python model itself.

  6. 6

    api.js sends the URL from the interface to the backend, which handles the work behind the website.

  7. 7

    routers/prediction.py receives the request and passes processing to the model service. The service coordinates work; it is not the trained model itself.

  8. 8

    predict.py uses the A2 feature rules and the loaded model to assess the new URL. The result travels back to the interface.

  9. 9

    ResultPanel.jsx displays the result and warning signs. The result supports assessment; it does not guarantee that a URL is safe.

02

Assignment 2 — from data to the complete model

A2 — follow the files step by step

Read from step 1 downwards. A/B/C indicate branches, not tasks that must execute one after another. This is the complete target architecture: CODE means reviewed evidence; PLAN/DESIGN means planned or proposed parts, not confirmed implementations.

  1. 1

    Basic_Datasets.zip is the course-provided data package. It contains the URL-and-label table used to begin the research.

  2. 2

    data_audit.py reads the ZIP, creates or verifies the raw copy, and checks for issues such as duplicates or conflicting labels. This identifies problems before cleaning.

  3. 2a

    reports/audit/summary.json stores the audit summary produced by data_audit.py. It is evidence for the report, not training input.

  4. 3

    malicious_phish.csv preserves the original table for comparison. The next step, data_cleaning.py, reads it without overwriting the original.

  5. 4

    data_cleaning.py trims whitespace, maps labels to the task target, quarantines conflicting records and removes duplicates. It produces a cleaned table for the next step.

  6. 5

    malicious_phish_cleaned.csv stores the cleaned output. feature_extraction.py reads its URLs to calculate features.

  7. 6

    feature_extraction.py converts URL characteristics into 36 numerical features. To do this, it calls url_parser.py at step 6a.

  8. 6a

    url_parser.py separates the URL into parts such as the domain and path, then returns them to feature_extraction.py. It analyses text without opening the destination website.

  9. 7

    url_features.csv stores the calculated feature table with labels and reference information. Labels are the answers; they must not be mixed into the features the model sees.

  10. 8

    04_eda.ipynb helps inspect and understand the feature table before splitting it. The notebook calls data_loading.py at step 8a instead of replacing reusable processing code.

  11. 8a

    data_loading.py reads the table, checks required columns, and separates features, labels and reference information. In this call it serves notebook exploration, not model training.

  12. 9

    data_splitting.py divides the data into train, validation and test. URLs sharing a domain stay in one set so that related examples do not appear in both learning and evaluation.

  13. 10A

    train.csv contains examples for model learning. The loader reads this file at step 11A.

  14. 10B

    validation.csv contains examples for comparing models and selecting assessment thresholds. The loader reads it at step 11B; it is not merged into train.

  15. 10C

    test.csv is reserved for final evaluation. It stays separate and is not used to select the model or thresholds.

  16. 11A

    data_loading.py reads train.csv, separates numerical inputs from labels, and supplies preprocessing and training. The loader only reads and organizes data.

  17. 11B

    data_loading.py reads validation.csv in the same way. train_classifier.py uses it for comparison and selection, not for fitting preprocessing rules.

  18. 11C

    data_loading.py reads test.csv when final evaluation begins and supplies it to evaluate.py. The three loader boxes represent the same file used in three different contexts.

  19. 12

    preprocessing.py prepares the numbers in the form the model needs. Transformation rules are learned from train; validation and test only reuse those rules. train_classifier.py coordinates this work.

  20. 13

    train_classifier.py trains models on train and compares them on validation. It selects a model and thresholds, then saves the choices in the files at steps 14 and 14a.

  21. 14

    selected_pipeline.joblib stores the selected model and fitted preprocessing. evaluate.py uses this existing pipeline on test without fitting it again.

  22. 14a

    selection.json records the chosen model, thresholds and when to report uncertainty. These decisions are locked before scoring on test.

  23. 15

    evaluate.py receives test from the loader, predicts with the selected model, and compares predictions with true labels. It records evaluation results without using test to adjust the model.

  24. 15a

    test_metrics.json stores numerical test results. The report and Insights page use these figures to explain the research results.

  25. 15b

    error_analysis.csv records incorrect predictions so the team can inspect model limitations. It is research error analysis, not a history of submitted user URLs.

  26. 16

    export_model.py packages the selected model and the information needed to use it after evaluation. It saves the A3 handover bundle without retraining on test.

  27. 17A

    final_pipeline.joblib is the model bundle A3 loads and uses. It contains both fitted preprocessing and the predictor.

  28. 17B

    model_metadata.json records accompanying information such as feature order, version and score interpretation. A3 reads it to use the model correctly.

  29. C1

    preprocessing.py is also used separately for clustering. The caller first selects one class from train and removes the label from the features; this branch learns transformation rules only from that selected data.

  30. C2

    cluster_urls.py groups URLs with similar features. It helps explain URL patterns in the research, rather than predicting labels as the main branch does.

  31. C3

    cluster_profiles.json describes the groups, including their sizes and characteristics. It supports the report and Insights; the website does not recluster data for every URL check.

  32. 18

    export_insights.py combines audit figures, model evaluation and cluster descriptions for the website. Its output is the file at step 19.

  33. 19

    reports/insights.json contains aggregate figures for the Insights charts. A2 therefore hands over both a prediction model and statistics explaining the research.

Use arrow labels to distinguish calls from data movement. A CSV does not execute Python. Test results do not feed back into model selection.
03

Assignment 3 — from user action to results

A3 — follow one URL submission and its result

The frontend is the browser interface; the backend receives and coordinates requests; ML uses the model to predict. Read branch S first to understand model preparation, then steps 1–18. Branch I is the separate statistics page.

  1. S1

    backend/app/main.py starts the backend and registers request endpoints. During startup it prepares the model service at S2.

  2. S2

    model_service.py keeps the model in memory and manages its use. It calls the bundle-loading part of predict.py.

  3. S3

    predict.py reads the A2 model and accompanying information, then gives the loaded bundle to the service. Loading happens at startup; it is not training again for each request.

  4. S4

    final_pipeline.joblib provides the model learned in A2. It is a file to read, not Python code that executes by itself.

  5. S5

    model_metadata.json supplies feature order, version and assessment rules to check that the bundle can be used. Once ready, the service is reused at step 11.

  6. 1

    index.html is the starting point when opening the website. It provides the application root and loads main.jsx.

  7. 2

    main.jsx mounts the React application and loads the root interface from App.jsx.

  8. 3

    App.jsx builds the shared application structure and uses router.jsx to choose the screen.

  9. 4

    router.jsx selects a page from the URL, such as Check URL or Insights. It uses the shared AppShell.jsx layout.

  10. 5

    AppShell.jsx displays navigation and the common frame while its contents change with the selected page. Choosing Check URL displays CheckUrlPage.jsx.

  11. 5a

    HowItWorksPage.jsx explains usage and system limitations. Simply reading this page does not run the model.

  12. 5b

    InsightsPage.jsx displays research statistics. Opening it follows the I1–I5 data-retrieval branch below.

  13. 6

    CheckUrlPage.jsx arranges the input, loading state, results and errors. It displays UrlForm.jsx to collect the URL.

  14. 7

    UrlForm.jsx receives the URL you type. Pressing Analyse passes that input to useUrlCheck.js.

  15. 8

    useUrlCheck.js manages the check: it validates input, sends a request if valid, and tracks loading and results. It also handles reset and prevents stale results overwriting a newer submission.

  16. 8a

    validation.js checks simple problems such as empty or overlong input. It returns its decision to the hook, which either calls the API or shows an error.

  17. 8b

    ErrorNotice.jsx displays errors passed through the hook and Check URL page. It handles both input errors and backend-call failures.

  18. 9

    api.js receives a valid URL and sends it to the backend through POST /api/predict. The interface shows a loading state while waiting.

  19. 10

    routers/prediction.py receives the backend request. The input must pass schema validation and a ready service must be obtained before processing.

  20. 10a

    schemas/prediction.py defines the expected request and response structure. The backend still validates the request even if the frontend already checked it.

  21. 10b

    dependencies.py retrieves the model_service.py instance prepared at startup. If it is not ready, the request must receive an error rather than a fabricated result.

  22. 11

    model_service.py receives the URL and coordinates prediction and explanation with the loaded model. It calls predict.py without rerunning A2 training.

  23. 12

    predict.py must convert the new URL into the same kind of features used during training. It calls feature_extraction.py, then sends those numbers through the model for prediction.

  24. 12a

    feature_extraction.py calculates features using the same A2 rules. It calls url_parser.py to obtain the URL structure.

  25. 12b

    url_parser.py splits the URL and returns the parts to the feature extractor. The calculated features then return to predict.py; the destination website is not opened.

  26. 12c

    explain.py is coordinated by the service to generate readable signals and highlight locations. These are observed signs, not automatic proof of why the model made its prediction.

  27. 13

    model_service.py merges the prediction and explanations into one result. This is the same service as step 11, now preparing its reply.

  28. 14

    routers/prediction.py receives the service result and returns it to the frontend in the agreed format. It does not need to echo the original URL.

  29. 15

    api.js receives the backend reply and passes the result or error to useUrlCheck.js. This is the return direction of the request sent at step 9.

  30. 16

    useUrlCheck.js ends the loading state and updates page state. CheckUrlPage.jsx uses that state to show either the result or an error.

  31. 17

    ResultPanel.jsx receives data from the Check URL page and arranges three elements: the score, the signal list and the highlighted URL.

  32. 18A

    ScoreBadge.jsx displays the score and a cautious assessment. Its wording must not guarantee that the URL is safe.

  33. 18B

    SignalList.jsx displays signals so users can understand which observed URL characteristics deserve attention.

  34. 18C

    UrlHighlight.jsx highlights relevant portions of the URL as text. It must not turn the input into executable content or automatically open it.

  35. I1

    api.js is called by InsightsPage.jsx to request statistics through GET /api/insights. This request does not submit a URL for checking.

  36. I2

    routers/insights.py receives the statistics request and calls insights_service.py to retrieve the figures.

  37. I3

    insights_service.py reads and validates the statistics file generated by A2. It does not calculate statistics from user scan history.

  38. I4

    reports/insights.json supplies aggregate data. It returns through the service, route and api.js to InsightsPage.jsx; the browser does not read the backend file directly.

  39. I5

    InsightsCharts.jsx receives the page data and draws the charts. This branch uses existing research results without retraining the model.

04

Testing and handover documents

Testing and handover — what does each file verify?

Rows 1–8 are independent checks, not a URL-processing sequence. test.csv assesses model prediction performance; the test files below check program behaviour. The diagram does not claim every proposed test has been implemented or passed.

  1. 1

    test_data_cleaning.py checks data_cleaning.py: whether fixtures are cleaned according to the rules, raw data remains unchanged, and repeated runs give consistent results.

  2. 2

    test_url_parser.py checks url_parser.py with different URL types, including malformed input. Parsing should work correctly without Internet access.

  3. 3

    test_feature_extraction.py checks feature_extraction.py: whether the expected columns exist and changing a label leaves the features unchanged. Labels must not become prediction inputs.

  4. 4

    test_data_splitting.py checks data_splitting.py: sets must not share domains and the split must be reproducible.

  5. 5

    test_prediction.py checks predict.py: a saved/reloaded model still works correctly, and processing raw URLs agrees with the prepared features.

  6. 6

    test_prediction_api.py checks the backend app through main.py: valid requests, invalid inputs and model-not-ready cases must be handled correctly.

  7. 7

    CheckUrlPage.test.jsx checks CheckUrlPage.jsx: loading, results, uncertainty, errors and reset should appear correctly.

  8. 8

    url-check.spec.js tests the full website with user-like interactions. main.jsx is the application entry point; the test is not limited to that individual file.

  9. 9

    test_metrics.json supplies test-set evaluation figures for the report. Error analysis and figures provide additional evidence for the conclusions.

  10. 9a

    cluster_profiles.json supplies group statistics and characteristics to explain clustering results in the report.

  11. 10

    assignment2-report.pdf presents methods, results and limitations using this evidence. It explains the research rather than providing execution instructions.

  12. 10a

    test-plan.md records what to test, the procedure and actual results. Do not mark checks as passed if they have not been run.

  13. 11

    README.md explains installation and how to rerun A2/A3, helping the recipient reproduce results and open the demo.

  14. 11a

    deployment.md explains frontend/backend startup, model paths and connections. The README links here for detailed demo instructions.

  15. 12

    meeting_minutes/*.md records team decisions and contributions. It supports the contribution records.

  16. 13

    contribution-form.docx summarizes contributions and follows the required template. The final A3 submission format still needs checking against the full specification.
